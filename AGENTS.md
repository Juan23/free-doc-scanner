This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Expo has changed — check the docs for this SDK

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Read the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`, or the installed source in `node_modules`.

## Commands

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
npx expo start              # start the dev server
npx expo lint               # lint
npx tsc --noEmit            # typecheck
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
```

While working, run the test files of the files you touch (`npx jest clean.test.ts`; there is no `test:changed` script); before a pull request or declaring a task done, run lint, typecheck and the full `npm test`.

## Building

Builds run locally from the project root. Use these two commands:

```bash
export LANG=en_US.UTF-8   # without it `pod install` stops on a Unicode normalization error
npx expo run:ios --device
```

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
export ANDROID_HOME="$HOME/Library/Android/sdk"
npx expo run:android --device
```

This Mac has no Java 17, so `/usr/libexec/java_home -v 17` fails; Homebrew's Java 21 builds debug and release (checked 2026-11-12, build 12).

A successful `expo run:ios|android` never exits: it keeps the dev server open after installing. The build is done when the log prints `› Opening <app> on <device>`; a failed build exits with an error. Run it in the background and wait on that line with Monitor.

For a store build, bump `ios.buildNumber` and `android.versionCode` in `app.json`, run `npx expo prebuild --clean`, then `./gradlew bundleRelease` in `android/` and `xcodebuild … archive` and `-exportArchive` in `ios/`. Run `xcodebuild -exportArchive` with `PATH=/usr/bin:/bin:/usr/sbin:/sbin`: Homebrew's `rsync` comes first otherwise, and the export stops with "Copy failed".

The iOS Simulator has no camera, so scanning on iOS needs a real iPhone. An Android emulator runs the camera screen and takes real photos. Start it with `-camera-back imagefile:<a 1200x1600 JPEG of a page> -gpu host`: its camera shows that picture after a few seconds, and the shutter saves it as 960x1280. The emulator reads the file again each time the camera opens, so to shoot a different page, overwrite the file and send the app to the home screen and back. Measured 2026-11-21 on the emulator's Android 16.

## This app

- Screens in `App.tsx` (Scans history, a 2-column grid of cards with a floating Scan pill; a scan's detail, and the camera screen), switched with state. There is no router. A scan's detail is a 2-column grid of page tiles (the page on a grey tile with a number chip, and an Add pages tile), a hint and a bottom bar with Save PDF and Save JPEG; its top bar has Scans, Select and a `⋯` button whose menu holds Delete scan (the confirmation Alert stays in `Root`). It has a Select mode: `Root` holds the picked page URIs (`picked`, null outside it), and `pagesToSave` in `save.ts` keeps them in page order, or every page when none are picked. Long-pressing a page also enters Select mode with that page picked, and in Select mode only picks it (`pickOnLongPress`). Select mode hides the hint, the `⋯` menu and Add pages; its top bar has Cancel (leaves it, changes no file), "N selected" and All, and the bottom bar has one Save or filter pill, disabled until a page is picked, that opens a bottom sheet (`Detail`'s `sheetOpen` and `panel` state) with Save as PDF, Save as JPEG, Filter these pages and Cancel (back to the picks). A save from the sheet runs `onSave` once the sheet has closed on iOS (Modal `onDismiss`), since the PDF folder picker can't present over a closing Modal. Filter these pages swaps the sheet for a dark panel with the page editor's strip (`FilterStrip`, shared) on the first picked page's previews, its filter read with `sharedFilter` in `clean.ts` (none checked when the picked pages differ), a Done pill, and above the panel the first picked page at the strength under the finger; a change goes through `filterPages` to the picked pages only and shows the "N pages changed" toast inside the panel. Tapping a page opens the page editor, a dark full-screen Modal over the detail: swipe between pages, Back and Done close it, Rotate turns the page shown, and holding the page shows its untouched photo (`heldPhoto` in `scans.ts`, the page itself when it has none).
- Scans are kept in the app's document folder (`scans.ts`): one folder per scan, named by its creation time in ms, holding its pages as `p1.jpg`, `p2.jpg`… and each page's untouched photo as `o1.jpg`, `o2.jpg`… (the page after upright turning, before any filter; older scans get one on their first filter change). There is no index file: the name comes from the folder name and the page order from the numbers. A page or original is replaced by writing `<name>.tmp` and moving it over the file, which deletes the old one first; listing a scan puts back a `.tmp` page or original whose file is gone, and deletes every other leftover write. An original's first copy is written as `<name>.part` instead, which listing always deletes and never puts back: it has no old file to move over, so a copy cut short must not pass for the photo.
- Saving is in `save.ts`: PDFs are built from the page JPEGs with `pdf-lib`; JPEGs go to Photos/Gallery. Tests sit next to each file.
- Scanning on both platforms is the app's own camera screen (shutter, a thumbnail with the page count, Done, and a corners screen with Retake, Next page and Done after each shot; the live view shows no page outline, since `expo-camera` gives no live frames, and `crop.ts` finds the page only after the shot), so every page is taken by hand. The system scanners can't do that: Apple's VisionKit (`CameraView.scanDocumentAsync`) has no option to open in manual capture (its Auto/Manual toggle starts on Auto), and Google's ML Kit scanner always opens in auto capture: it ignores its capture-mode extra, and also its initial-images extra, so it can't be fed our photos either (both checked on Play services 26.41, 2026-11-04). `crop.ts` finds the page's corners in each photo (on a 300 px copy: straight edge lines found with a Hough transform, and the four that best frame a convex page with edges all round; the whole photo when none stands out. Brightness alone let glare on a pale table join the page: on 119 SmartDoc frames (`SMARTDOC=<the smartdoc-sample folder> npx jest smartdoc.test.ts`) all four corners land within 5% of the diagonal on 97.5% of frames (31.1 ms/photo), against 24% before) and straightens the page inside the corners with a Skia perspective matrix. Its tests run on real pixels like `clean.ts`'s.
- Clean-up is in `clean.ts`: Skia whitens each new page right after it is stored, from its untouched original, replacing the page file. Faint marks stay only near writing. Writing is found twice on the 500 px copy: from its average darkness, and, for thin pale print the average misses, from the darkest photo pixel under each small pixel where its 8 x 8 samples leave both a clear row and a clear column (letters do; a straight crease or a speck far from text does not). The paper beside such letters whitens at that strength like any other, and their dark cores stay: grey 140 to 165 print on grey 220 paper at 24 to 44 px on a 3024 px page, at Normal and Strong. It also whitens what shows past bent or curled page edges: what touches the border, differs from the paper in the middle of the page, stays shallow and bends smoothly like a paper edge. Print the crop cuts into has walls (letters, bands, pictures) or runs straight along a side, so it stays. A table or carpet round the page, as where `crop.ts` finds no page and the frame is the whole photo, is whitened too, at every strength (`markDarkBackground`). On the small copy the page is the largest patch lighter than half of the frame's paper (its 90th percentile of luma), with any patch a tenth its size that is clear of the border (paper a band across the page cuts off); together they must hold half of the frame's light pixels, and the page may run off the photo's edge. What is darker than that cutoff and lies outside the page's convex hull may be table. A reference stays put, so a surface never creeps across a printed edge or round a printed corner; only beyond reach, where light shades a table slowly, it moves on to a pixel that has drifted half that far and has pixels of its own colour 3 px away in all 8 directions. A `Filter` picks Original, Clean or Grayscale and a strength from 0 (Light) through 1 (Normal) to 2 (Strong); in between, each `KEEP` number lies straight between the two steps around it, and 0, 1 and 2 are exactly the steps. The choice for new scans is JSON in a `filter` file in the document folder; missing it means Clean, Normal, and an old `clean-up-off` file is read once as Original and deleted. `filterImage` does the filtering in memory, at any width, and writes no file: a stored Clean or Grayscale page is it at full size, and a stored Original is a byte copy of the photo it shrinks for a preview, so a small preview of a filter matches the page it would store. A preview narrower than 500 px is cleaned at 500 px and then shrunk (cleaning at the preview's own few pixels broke text into fragments), so its text stays whole; a hairline the full-size pass keeps can still vanish from it (a 0.8 px grid on a 3024 px photo; it shows from a 1600 px one), and so do pale 1 and 2 px table lines, which are kept only on a page 1000 px wide or more. It must be given the full untouched photo, not a thumbnail: the paper and ink are measured on a small copy of what it is given. Its tests run on real pixels through Skia's CanvasKit Jest environment.
- Each page keeps the filter it was last given as JSON in `f<N>.json` beside `p<N>.jpg` (`pageFilter` in `clean.ts`; missing or unreadable means none, as for older pages). `cleanPages` writes it after each page changes, so new scans and the strip both record it; `listScans` ignores it. The page editor has a strip of Original, Clean and Grayscale radios under the pager. Their thumbnails are `filterPreviews`: Normal strength, made from the page's full untouched photo (`heldPhoto`), recomputed a moment after the page or its turn count changes (a filter change keeps them), and disposed when replaced or when the editor or the filter panel closes. Tapping another thumbnail filters that page at Normal at once; tapping the selected Clean or Grayscale shows or hides the strength slider (`@react-native-community/slider`, Light to Strong with a mark at Normal, which it snaps to within 0.1), which filters the page or the picked pages when the finger lifts; a step from a screen reader or a keyboard comes with no touch, so each one is applied, without the snap to Normal. As the finger moves, `strengthPreview` in `clean.ts` filters the first one's untouched photo at that strength at full size, as storing does, on the GPU (the paper and edge analysis is measured once per run), shrinks it to the screen, and shows it over the page (hidden while the page is held or the pager is swiped), or in Select mode above the filter panel; only the latest move waits while one runs. Opening the slider already draws it at the page's strength, so the first move does not wait for the photo and the GPU's first draw. Select mode previews only the first picked page (its heading says so): each page filtered per move would multiply the GPU work, and the strip's thumbnails are already the first page's. A narrower pass would drop the thin strokes and pale table lines the stored page keeps. On lift it shows the strength being stored and frees the photo before the store starts (`finish`; action controls — the filter strip, Rotate, Use on all, and detail/sheet actions — are disabled meanwhile, while Back, Done, the Select panel's Done and swipes stay enabled, so nothing else takes the store's turn), and then stays: in the editor until the stored page has loaded in the pager, in Select mode until the next change. A store turned away by another action, or one that fails, clears it. While the slider stays open, a fresh run is warmed up whenever none is going and no store is running (after a store, a turn or a hide), so the next drag does not wait either. A photo that cannot be read or filtered clears the preview and ends the run; no warm-up retries it until the page changes, though the next move does. The hook is `useStrengthPreview.ts`, the order around a store `previewSession.ts`; the images it hands to the screen are freed by `liveImages.ts`, only once a render has replaced them. On the Simulator the GPU pass and the CPU pass that stores the page differ by 0.1 to 0.2 grey levels on average at strengths 0.6, 1.6 and 2, no pixel by more than 32, and at most 0.021% of pixels fall on the other side of mid-grey (2026-11-14). The last filter picked in the strip, or used through "Use on all", becomes the default for new scans. The page editor's "Use on all N pages" button (hidden for a one-page scan or a page with no recorded filter) applies that page's filter to every page, and toasts "N pages changed" inside the editor.
- Turning pages is in `upright.ts`: `rotatePage` turns a stored page and its untouched original by quarter turns; `uprightPages` turns sideways or upside-down text pages upright. On a small copy it reads which way is up from two things that must agree: Latin text's ascenders and capitals outnumbering its descenders, and full stops and commas sitting on the baseline with a space after them. Strokes alone would turn upright Cyrillic upside down, since its descenders outnumber its ascenders. Some scripts' letters look like full stops (Hebrew's yod hangs from the top of the line like one upside down); such marks also come inside words, alone between wide gaps in a typewriter font, and right-to-left text has its full stops spaced the other way (a mark with a space each side counts as such only when the wider is at least three times the other, and as neither when it is two to three times: on the small copy, a comma after a y has a 4 px gap before it and 11 after, in 36 px type on a 3024 px photo), so where those together number at least 4 and reach two thirds of the full stops it leaves the page as it is. So it does where the strokes lean further than Latin ever does (vowel points under every letter), and where the turned letters would be heavier at the bottom than at the top, as Hebrew's are upside down (their bars run along the top). It leaves a page as it is when unsure (no text, capitals only, other scripts, text without full stops): turning an upright page is worse than missing a turned one. Its tests draw real text with CanvasKit's default typeface, with macOS's Times New Roman, Arial and Courier New (Latin, Cyrillic, Hebrew) when present, and a made-up script of blocks for Hebrew's yod. On 3024 px pages in 24 to 56 px type, Times New Roman and Arial Latin turn upright from 32 and 28 px; Courier New's Latin at 40 and 44 px, and at 48 px at 1 and 2 quarter turns only, since at 24 to 28 px its strokes are too thin to find lines, at 32 px its marks look like another script's, at 36 px its balance and full stops fail, and at 52 to 56 px no full stops count; Cyrillic and Hebrew are left as they are at 24 to 56 px, also with the script-mark and heavy-bottom rules off. On real phone photos it turns few pages: `DOCUNET=<the docunet-original folder> npx jest uprightphotos.test.ts` crops photos 1_1 to 15_2 as the app does and turns each by 90, 180 and 270 degrees, and 4 of those 90 copies come back upright (it fails below 4), with no upright photo turned and none turned the wrong way; with `FIRST=16 LAST=65`, 21 of 300 come back and none of 400 is wrong. `findPage` finds the page on 8 of the first 30 photos, and 4 of those 24 copies come back. The text on a page crop is 3 to 12 px high on the 1000 px copy, so few strokes and full stops are counted. `App.tsx` runs it on new pages before the chosen filter, whether that keeps the photo or not, and the page editor has a Rotate button. A page edited on screen (turned or filtered) is shown from its URI plus `?v=<n>`, the edit counter: an Image on screen reloads only when its URI changes, Android's Fresco also caches by the whole URI, and both platforms read a `file://` image by its path, ignoring the query.

## Test photos

Public sets of real document photos for testing `crop.ts` and `clean.ts` on the Mac. They stay out of git (size, and DocUNet has no license) and never ship in the app.

- `smartdoc-sample/`: the sample of the [SmartDoc 2015 Challenge 1](https://zenodo.org/records/1230218) set (CC BY 4.0, credit the authors): `.avi` videos of pages on tables in `input_sample/`, and each frame's true page corners as XML in `input_sample_groundtruth/`. Pull frames out of the videos to test with.
- `docunet-original/`: 130 [DocUNet](https://www3.cs.stonybrook.edu/~cvl/docunet.html) photos of bent, creased and folded pages, two per page (`64_1.jpg`, `64_2.jpg`).
- `npx jest inkkeep.test.ts` with `DOCUNET=<a photo folder>` scores Clean on each photo without looking at it: the share of pale and dark print kept, and of paper whitened near and away from print. Its `FLOORS` are set for `docunet-original/` only. It fails when the means there, whole or a `SHARD=i/4` quarter, fall below them. Other splits only score. `CLEAN=<module>` scores another copy of the filter, `OUT=<file>` collects the lines.
- `docunet-scan/`: the 65 flatbed scans of those pages (`64.png`), the right answer for each photo. Others report that the last two photos (page 64) are upside down compared with their scan; check before scoring them.

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally.
- Prefer recommended Expo modules over third-party libraries. Docs: https://docs.expo.dev/versions/latest/index.md
- No accessibility work until the app is fully usable (owner, 2026-11-21): no screen reader runs and no accessibility issues. Keep the labels the code already has.
